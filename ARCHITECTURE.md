# talking_bot — архитектура

Ассистент переговоров в Telegram: держит контекст переписки по каждому
контрагенту, готовит черновики ответов и **не даёт отправить уступку**, не
предусмотренную планом — включая уступку, которую вписал ты сам.

---

## 1. Главное архитектурное решение

Проверяющий модуль (`guard`) стоит **на выходе, а не рядом с черновиком**.

```
                        ┌──────────────────────────────┐
   входящее ─────────▶  │ compose (Claude)             │
   от заказчика         │ план + история + тон → текст │
                        └──────────────┬───────────────┘
                                       ▼
                        ┌──────────────────────────────┐
   твой правленый ────▶  │ GUARD (Claude, отдельный    │
   текст ───────────┐   │ вызов, БЕЗ истории)          │
   твой свой текст ─┘   │ план vs текст → вердикт      │
                        └──────────────┬───────────────┘
                          in_plan │ concession │ red_line
                                  ▼        ▼         ▼
                              отправка  подтв.   блок +
                                        +лог     фраза-подпись
                                       ▼
                                 Telegram → заказчик
```

Почему так, а не «Claude пишет строгий черновик, а ты жмёшь кнопки»: кнопка
«Изменить» — это ровно тот канал, через который ты уже прогнулся один раз.
Строгий черновик её не закрывает. **Ни один байт не уходит в Telegram, не
пройдя `guard`** — ни от модели, ни от тебя.

Второе: `guard` вызывается **отдельным запросом и не получает историю
переписки**. На входе только активный план и текст-кандидат. Модель, которая
видит, как заказчик третье сообщение подряд давит на сроки, начинает «входить в
положение» — это её нормальное поведение и здесь оно вредно. Прокурор без
контекста не сочувствует.

## 2. Процессы и адаптеры

Два сменных интерфейса — этим закрывается вопрос «начинать с userbot или без».
Это не две разные системы, а две реализации двух классов.

| Слой | Стадия 1 (без userbot) | Стадия 2 (userbot) |
|---|---|---|
| `ingest` | `ForwardIngest` — форвардишь сообщение боту | `TelethonIngest` — читает твою личку |
| `egress` | `ManualEgress` — бот отдаёт готовый текст, копируешь | `TelethonEgress` — шлёт от твоего имени |

Ядро (`compose` → `guard` → журнал) одинаковое. Стадию 2 включаешь флагом в
конфиге, когда стадия 1 отработает на реальной переписке.

Процессы:

- `app.py` — один asyncio-процесс: aiogram polling + (опционально) Telethon
  client в том же loop.
- Postgres — история, планы, вердикты, аудит.
- Alembic — миграции.

## 3. Модель данных (Postgres)

```
counterparties  id, tg_user_id, name, notes
dialogs         id, counterparty_id, title, topic_id, state,
                summary, summary_upto_msg_id, style_card  -- JSONB
messages        id, dialog_id, direction(in|out), tg_message_id,
                text, sent_at, source(forward|telethon)
plans           id, dialog_id, version, created_at, active, changelog
plan_items      id, plan_id, code, title, value,
                kind(red_line|target|flexible), fallback, breach_signal
drafts          id, dialog_id, in_reply_to, text, origin(model|user),
                status(pending|sent|discarded)
verdicts        id, draft_id, subject(model_draft|user_edit),
                status(in_plan|concession|red_line), items JSONB, rationale
deviations      id, dialog_id, plan_item_id, draft_id, reason,
                confirmed_at         -- append-only, ничего не удаляется
audit           id, actor, action, payload JSONB, at
```

Два узла, которые несут смысл:

- **`plans` версионируются.** План не редактируется по ходу разговора. Хочешь
  сменить условие — коммитишь новую версию с `changelog`. Разница между
  «передумал» и «прогнулся» становится строкой в базе.
- **`deviations` — append-only.** Каждый твой обход `guard` записывается с
  причиной. Бот показывает накопленный список: «по этому диалогу уже отдано:
  3-й круг правок бесплатно (14.08), срок −5 дней (19.08)». Это единственная
  защита от медленного дрейфа, который ты у себя заметил.

## 4. Контекст: как помнится вся переписка

Полная история лежит в Postgres. В промпт целиком не едет — едет так:

```
system[0]  (cache, ttl=1h)  роль + правила + активный ПЛАН + красные линии
system[1]  (cache)          style_card + rolling summary старой части
messages                    последние N=30 сообщений дословно + новое
```

- `rolling summary` пересчитывается каждые K=20 сообщений отдельным вызовом и
  лежит в `dialogs.summary`. Дословно — только свежий хвост.
- `style_card` — извлекается один раз из истории и правится руками: ты/вы,
  средняя длина, эмодзи, приветствия, привычные обороты, скорость ответа. Это
  и есть «тон предыдущего диалога» в машинном виде, а не пожелание в промпте.
- Кэш префикса даёт ~10x экономии на входе. Порядок рендера: `tools` →
  `system` → `messages`, любое изменение байта в префиксе рвёт кэш ниже. Поэтому
  никаких `datetime.now()` и несортированного `json.dumps` в system.
  Проверка живая: `response.usage.cache_read_input_tokens` > 0.

## 5. Вызовы Claude

Все — `claude-sonnet 4`, `thinking={"type": "adaptive"}`, ответ через structured
output (Pydantic), чтобы вердикт был данными, а не текстом для чтения глазами.

**compose** — `client.messages.parse(..., output_format=Draft)`

```python
class Draft(BaseModel):
    text: str                    # готовый ответ заказчику
    addresses: list[str]         # какие его тезисы закрыты
    concessions: list[str]       # что модель сама считает уступкой
    open_questions: list[str]    # что осталось не отвечено
```

**guard** — отдельный вызов, вход: только план + текст-кандидат

```python
class Violation(BaseModel):
    plan_item_code: str
    kind: Literal["concession", "red_line"]
    quote: str                   # цитата из текста
    why: str

class Verdict(BaseModel):
    status: Literal["in_plan", "concession", "red_line"]
    violations: list[Violation]
    rationale: str
```

`effort: "high"` на compose, `"medium"` хватает guard. Вход guard короткий
(план + один текст) — он дешёвый и должен вызываться на каждый исходящий текст,
включая твой собственный.

**summarize** — обновление `dialogs.summary` раз в K сообщений.

Порядок цены: ~30k входа из кэша + ~600 выхода на compose плюс короткий guard —
**около 5 центов за обработанное сообщение**. Сто сообщений переписки ≈ $5.

## 6. Операторский интерфейс

«Отдельное окно на пользователя» в Telegram делается **форум-топиками**:
заводишь супергруппу с включёнными топиками, бот админ с `manage_topics`, на
каждого контрагента создаётся свой топик. Получаешь настоящие раздельные
переписки с прокруткой истории, а не переключение контекста кнопкой.
Альтернатива для стадии 1 — `/dialogs` со списком и активным диалогом в FSM.

Карточка черновика в топике:

```
┌────────────────────────────────────────┐
│ Заказчик: сроки, «давай к 15-му»       │
├────────────────────────────────────────┤
│ Черновик ответа...                     │
├────────────────────────────────────────┤
│ 🔴 п.2 «срок ≥5 недель»                │
│    цитата: «постараюсь успеть к 15-му» │
├────────────────────────────────────────┤
│ [Отправить] [Изменить] [Переписать]    │
│ [Свой текст] [Пропустить]              │
└────────────────────────────────────────┘
```

Поведение по статусу вердикта:

- `in_plan` — «Отправить» активна.
- `concession` — отправка после явного подтверждения; пишется в `deviations`.
- `red_line` — **отправка заблокирована**. Разблокировка: ввести причину
  текстом и повторить кодовую фразу пункта (`НАРУШАЮ П.2`). Одна кнопка этого
  не делает — трение здесь намеренное.

«Изменить» и «Свой текст» уходят на тот же `guard`. Обхода нет.

    ingest/        base.py  forward.py  telethon_ingest.py

                   style.py  prompts/*.md

Промпты — отдельными `.md` файлами под git. Они меняются чаще кода, и их
история нужна: «почему бот стал мягче» отвечается диффом.

## 8. Риски

- **Telethon на личном аккаунте.** Автоматизация личного номера — основание
  для ограничений со стороны Telegram. Смягчение: только чтение + отправка по
  твоей кнопке, никаких автоответов, человеческие задержки, лимит
  сообщений/мин. Полностью риск не снимается. Второй номер не спасает: переписку
  с заказчиком нельзя продолжить с другого аккаунта.
- **`guard` даёт ложные срабатывания.** Лечится не понижением строгости, а
  качеством `plan_items`: у каждой красной линии должны быть `breach_signal`
  (по какому признаку считать нарушением) и `fallback` (что делаешь, если
  заказчик упрётся). Пункт без них — пожелание, и guard на нём будет шуметь.
- **Нет плана — половина системы мертва.** `plan_items`, `guard`, `deviations`
  без письменного плана не работают. Это первый рабочий артефакт, не код.
- **Задержка.** compose + guard на Opus 5 — это секунды, не мгновенно. Для
  переписки с заказчиком нормально; для «онлайн-чата» — нет.
