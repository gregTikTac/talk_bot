## Шаг 1 — окружение

**Что сделали.** Поставили Python-окружение (venv) и библиотеки:

| Библиотека | Зачем |
|---|---|
| `aiogram` | сам Telegram-бот — принимает и отправляет сообщения |
| `sqlalchemy` + `asyncpg` | работа с базой данных Postgres из Python |
| `alembic` | миграции — способ менять структуру базы без ручного SQL |
| `pydantic` / `pydantic-settings` | проверка данных и чтение настроек из `.env`-файла |
| `anthropic` | вызов Claude — для черновиков ответов и проверки guard |

**Почему venv, а не системный Python.** Чтобы версии библиотек этого проекта не конфликтовали с другими программами на машине. Стандартная практика в Python — не ставить пакеты "в систему".

## Шаг 2 — конфигурация (`src/talking_bot/config.py`)

**Что сделали.** Один класс `Settings`, который читает токен бота, ключ Anthropic и адрес базы данных из файла `.env` (файл ты создашь сам — в нём секреты, поэтому он не должен попадать в git).

**Почему так.** Секреты (токены, пароли) никогда не пишутся прямо в код — только читаются из окружения. Если код случайно попадёт в чужие руки, токены в нём не утекут.

**Что нужно от тебя.** Файл `.env` в корне проекта с тремя строками:
```
BOT_TOKEN=токен_от_BotFather
ANTHROPIC_API_KEY=твой_ключ
DATABASE_URL=postgresql+asyncpg://user:password@localhost/talking_bot
```

## Шаг 3 — модель данных (`src/talking_bot/db/models.py`)

**Что сделали.** Описали 8 таблиц будущей базы данных на языке Python (SQLAlchemy сама превратит это в SQL). Пока это только "чертёж" — реальной базы ещё нет, до неё дойдём на следующем шаге через Alembic.

**Таблицы и зачем каждая:**

- **`counterparties`** — контрагенты (заказчики), с кем ведёшь переписку.
- **`dialogs`** — один диалог с одним контрагентом. Здесь же лежит `summary` (сжатый пересказ старой части переписки — чтобы не гонять всю историю через Claude каждый раз) и `style_card` (тон переписки: на «ты»/«вы», длина сообщений, обороты — извлекается один раз и правится руками).
- **`messages`** — все сообщения, входящие и исходящие.
- **`plans`** — план переговоров. **Версионируется**: план не редактируется на лету, любое изменение условия — это новая строка с новым номером версии и `changelog` (объяснением, что и почему изменилось). Так на бумаге видна разница между «заказчик передумал» (новая версия с обоснованием) и «я прогнулся» (обход проверки без объяснения).
- **`plan_items`** — пункты плана. Три вида: `red_line` (не обсуждается), `target` (к чему стремимся), `flexible` (можно менять). У `red_line`-пунктов должны быть заполнены `fallback` (что делаешь, если контрагент упёрся) и `breach_signal` (по какой фразе/признаку считать пункт нарушенным) — без этого guard (модуль-проверяльщик, опишу дальше) будет либо молчать, либо шуметь просто так.
- **`drafts`** — черновики ответов, ещё не отправленные. `origin` показывает, кто написал — модель или ты сам (когда правишь черновик или пишешь свой текст).
- **`verdicts`** — вердикт guard по каждому черновику: `in_plan` (в рамках плана), `concession` (уступка), `red_line` (нарушение красной линии). Хранится отдельно от черновика, потому что один черновик может проверяться заново после правки.
- **`deviations`** — **ничего не удаляется, только дописывается**. Каждый раз, когда ты сознательно обходишь guard и всё равно отправляешь уступку — это пишется сюда с причиной. Это единственное место в системе, которое накапливает историю твоих уступок и не даёт ей потеряться в отдельных диалогах.

**Проверка.** Импортировал модели, SQLAlchemy собрала все 8 таблиц без ошибок — структура непротиворечива.

## Шаг 4 — база данных через Docker (`docker-compose.yml`)

**Что сделали.** Один файл, который поднимает Postgres в контейнере одной командой:
```
docker compose up -d
```

**Почему Docker, а не ставить Postgres в систему.** Через Docker Postgres живёт изолированно — не конфликтует с другими программами, легко удаляется целиком (`docker compose down -v`), и точно такая же команда поднимет базу на другой машине. Данные не теряются между перезапусками — они лежат в отдельном docker-томе `pgdata`.

**Логин/пароль/адрес** — простые (`talking_bot`/`talking_bot`), потому что база торчит наружу только на локальной машине для разработки. На боевом сервере (когда дойдём до деплоя) пароль будет другим и порт наружу открыт не будет.

**`.env` и `.env.example`.** `.env` — реальные секреты (токен бота, ключ Anthropic, адрес базы), в git не попадает — он в `.gitignore`. `.env.example` — тот же файл, но с плейсхолдерами вместо секретов, можно смело класть в git, чтобы другой человек знал, какие переменные нужны.

## Шаг 5 — миграции (Alembic)

**Что сделали.** `alembic init alembic` создал стандартный каркас, но пришлось его донастроить под наш случай — стандартный шаблон Alembic не умеет работать с асинхронным подключением к базе (`asyncpg`), а наш проект целиком асинхронный (aiogram и SQLAlchemy 2.0 async).

**Что изменили в `alembic/env.py`:**
- подключили наши модели (`Base.metadata` из `db/models.py`) — иначе Alembic не знает, какие таблицы должны быть;
- подключили `settings.database_url` из `.env` — иначе пришлось бы дважды хранить адрес базы (в `.env` и в `alembic.ini`);
- заменили синхронный `engine_from_config` на `async_engine_from_config` — под наш `postgresql+asyncpg://` адрес.

**Что такое миграция простыми словами.** Это файл-инструкция «как изменить структуру базы» (создать таблицу, добавить колонку и т.д.), под контролем версий — как git, только для структуры БД. Каждая миграция знает, какая шла до неё, поэтому базу можно накатить с нуля или обновить по шагам.

**Что сделали:**
```
alembic revision --autogenerate -m "initial tables"   # сравнил models.py с пустой базой, сгенерировал миграцию
alembic upgrade head                                    # применил её — создал все 8 таблиц в Postgres
```

**Проверка.** Зашёл в контейнер и посмотрел список таблиц напрямую (`\dt` в psql) — все 8 таблиц на месте, плюс служебная `alembic_version` (Alembic хранит в ней, какая миграция сейчас применена).

## Шаг 6 — подключение к базе (`db/session.py`)

**Что сделали.** Функция `get_session()` — единственная точка входа в базу для всего остального кода. Открывает подключение, отдаёт его тебе, а по выходу сама сохраняет изменения (`commit`) или откатывает их, если внутри была ошибка (`rollback`).

**Почему так, а не просто открывать подключение где попало.** Если в середине операции (например, "создать диалог и записать первое сообщение") что-то упадёт, без отката в базе останется диалог без сообщения — наполовину сделанная работа. `get_session()` гарантирует: либо всё сохранилось, либо ничего.

## Шаг 7 — работа с диалогами и планами (`domain/dialog.py`, `domain/plan.py`)

**Что сделали.** Функции, которыми будет пользоваться бот — не «сырой» SQL, а понятные операции:

- `get_or_create_dialog` — по Telegram ID контрагента найти его диалог или завести новый, если пишет впервые;
- `add_message` / `get_recent_messages` — записать сообщение и получить последние N в правильном порядке (старые сначала — так их удобно отдавать в Claude);
- `create_new_plan_version` — завести новую версию плана. Старая версия не удаляется, просто помечается неактивной (`active = False`) — вся история версий остаётся в базе;
- `get_active_plan` / `get_plan_items` — прочитать текущий действующий план и его пункты.

**Почему план версионируется, а не редактируется на месте.** Уже писал в шаге 3, здесь это заработало на практике: чтобы сменить условие, нужно явно вызвать `create_new_plan_version` с `changelog` — нельзя незаметно поправить старую версию.

## Баг №1 — часовые пояса не совпали

**Что случилось.** Первый же тест упал с ошибкой `can't subtract offset-naive and offset-aware datetimes`. Это хорошая ошибка — она поймала реальную проблему, а не спрятала её.

**В чём была причина.** В коде время бралось как `datetime.now(timezone.utc)` — «дата и время плюс явная отметка, что это UTC». А колонка в базе была создана как `TIMESTAMP WITHOUT TIME ZONE` — «дата и время без какой-либо отметки о часовом поясе». Postgres/asyncpg не пытается угадать, что имелось в виду, и отказывается писать одно в другое.

**Как исправили.** Все колонки со временем в проекте (`sent_at`, `confirmed_at`) явно объявлены как `DateTime(timezone=True)` — то есть база тоже хранит часовой пояс. Теперь и код, и база одинаково понимают время. Правило на будущее: **все времена в проекте — в UTC и с явным часовым поясом**, без исключений.

**Как проверили, что не сломалось.** Написал сквозной тест: создать контрагента → диалог → план с красной линией → два сообщения — в одном соединении с базой, потом **открыл новое соединение** и прочитал всё обратно. Это принципиально: если бы читал в том же соединении, мог бы увидеть данные из памяти Python, а не то, что реально осело в Postgres. После фикса тест прошёл целиком.

## Шаг 8 — подключение к Claude через OpenRouter (`llm/client.py`)

**Что сделали.** Один объект `client` на весь проект — все вызовы к Claude идут через него.

**Почему OpenRouter, а не Anthropic напрямую.** У тебя уже есть аккаунт и оплаченный баланс на OpenRouter (ты сам через него раньше подключал GPT-4 mini) — не нужно заводить второй отдельный счёт и следить за балансом в двух местах. Плата за удобство: OpenRouter — это OpenAI-совместимый API, а не родной Anthropic. Из-за этого нет удобного помощника `messages.parse()`, который сам превращает ответ модели в Pydantic-объект — пришлось делать это вручную (см. следующий шаг). SDK для этого используется `openai` (он занимается только формой запроса, сама модель как была Claude, так и осталась).

**Как проверил имя модели, а не угадал.** Названия моделей на OpenRouter пишутся как `провайдер/модель` и не всегда совпадают с официальными именами Anthropic. Прежде чем писать код на угадывании, запросил у самого OpenRouter список доступных моделей (`client.models.list()`) и нашёл в нём точную строку `anthropic/claude-opus-5`. Так надёжнее, чем полагаться на память.

## Шаг 9 — guard (`llm/guard.py`)

**Что сделали.** Функция `check_draft(plan_items, candidate_text)` — отдельный вызов Claude, который проверяет один текст-кандидат на соответствие плану и возвращает структурированный вердикт: `in_plan` / `concession` / `red_line`, с указанием, какой именно пункт нарушен, дословной цитатой и объяснением.

**Почему guard не видит историю переписки — только план и сам текст.** Это ключевое архитектурное решение всего проекта. Модель, которая видит, что заказчик третий раз подряд давит на сроки, начинает по-человечески "входить в положение" — это нормальное поведение языковой модели, и здесь оно вредно. Проверяющий без контекста переписки не сочувствует, он просто сверяет текст с планом.

**Почему план может быть пустым и это не значит "всё разрешено".** Если пунктов плана ещё нет, guard не пропускает текст молча как `in_plan` — он явно возвращает `concession` с пояснением "план пуст, проверить не по чему". Это заставляет писать план раньше, чем начинать реальную переписку, а не полагаться на то, что пустая проверка = зелёный свет.

**Как получаем структурированный ответ через OpenRouter.** Родной Anthropic SDK умеет `messages.parse(..., output_format=Verdict)` — сам гарантирует, что ответ ляжет в Pydantic-схему. Через OpenAI-совместимый API так не получится: попросил модель вернуть строгий JSON (`response_format={"type": "json_object"}` + подробное описание нужной структуры прямо в промпте), а затем распарсил ответ через `Verdict.model_validate(json.loads(...))`. Если модель вернёт JSON неправильной формы — Pydantic сам упадёт с понятной ошибкой, а не пропустит мусор дальше молча.

**Как проверил.** Три сценария на реальном вызове Claude через OpenRouter:
1. Пустой план + текст со скидкой → `concession` с объяснением "план пуст". Не `in_plan` по умолчанию — как и задумано.
2. Заполненный план (красные линии: бюджет ≥25000, срок 3 недели) + безобидный текст, который просто повторяет условия плана → `in_plan`, нарушений ноль.
3. Тот же план + текст с явным нарушением обеих красных линий одновременно ("сделаем за 20000 и уложимся в 2 недели без доплаты") → `red_line`, обе линии пойманы отдельно, с точной цитатой и причиной по каждой.

Все три прошли верно с первого раза после исправления под OpenRouter.

## Шаг 10 — compose (`llm/compose.py`)

**Что сделали.** Функция `compose_draft(dialog, plan_items, recent_messages)` — составляет черновик ответа заказчику. В отличие от `guard`, этот вызов **видит** и план, и историю переписки (последние сообщения плюс сжатый пересказ более старой части и карточку стиля — на "вы" или на "ты", короткие фразы или длинные).

**Почему у compose и guard разные права на контекст.** Это прямое следствие решения из шага 9. Чтобы ответ звучал живо и в тон разговора, черновику нужна история. Но именно поэтому черновику нельзя доверять самому решать, не нарушает ли он план, — он видит тот же контекст, из-за которого человек начинает уступать. Разделение ролей: `compose` пишет хорошо, `guard` проверяет строго, и он не имеет доступа к тому, что могло бы его смягчить.

**Что возвращает compose, кроме текста.** Черновик сам себя описывает: `addresses` (какие тезisы заказчика закрыты), `concessions` (что модель сама считает уступкой — это её собственная самооценка, не заменяет проверку guard), `open_questions` (что осталось без ответа). Это не для показа заказчику — это для тебя, чтобы видеть в карточке черновика, чего в нём не хватает, ещё до того как его проверит guard или прочитаешь ты сам.

**Как проверил — не на нейтральном тексте, а на провокации.** Собрал реалистичную историю (по мотивам твоей настоящей переписки): заказчица просит скомбинировать дорогой вариант по цене дешёвого — это прямое попадание в `breach_signal` пункта плана. Черновик не согласился, использовал прописанный в плане `fallback` ("начать с варианта 1, кадры доплатой отдельным шагом"), и получил от `guard` вердикт `in_plan` без единого нарушения. Это первая сквозная проверка связки `compose → guard` на входных данных, которые специально должны были спровоцировать уступку.

## Шаг 11 — пайплайн (`service/pipeline.py`)

**Что сделали.** Функция `run_pipeline` — единственный путь от входящего сообщения к готовой карточке: записать сообщение в базу → `compose_draft` (черновик) → `check_draft` (проверка) → сохранить и черновик, и вердикт в базу со связкой между ними. Отдельная функция `recheck_edited_text` делает то же самое для твоей правки или твоего собственного текста — без compose, потому что писать уже не нужно, только проверить.

**Почему это отдельный модуль, а не код прямо в обработчике бота.** Пайплайн не должен знать про Telegram, а обработчик бота не должен знать про внутренности LLM-вызовов. Если позже появится второй канал ("проверить черновик из веб-интерфейса", например) — он сможет вызвать тот же `run_pipeline`, не трогая код Telegram-бота.

**Как проверил.** Прогнал реалистичную ситуацию: план с красной линией по цене (25000, ниже — нельзя), входящее сообщение с прямым давлением ("у меня бюджета больше нет, сделайте за 15000"). Черновик не согласился на цену, использовал прописанный fallback (урезать объём, не цену), guard подтвердил `in_plan`. Проверил не только текст на экране, но и то, что реально осело в таблицах `drafts` и `verdicts` — они связаны верно.

## Шаг 12 — Telegram-бот (`control/`, `app.py`)

**Что сделали.** Первую живую версию бота на aiogram — стадия 1 из архитектуры, без userbot. Три файла:

- **`control/keyboards.py`** — кнопки под карточкой черновика. У кнопки "Отправить" есть исключение: если вердикт `red_line`, кнопки нет вообще. Это не забытая деталь — так и задумано архитектурой: нарушение красной линии нельзя отправить одним нажатием.
- **`control/states.py`** — одно FSM-состояние `EditDraft.waiting_for_text`. Когда ты жмёшь "Изменить", бот запоминает, какой черновик редактируешь, и ждёт следующее твоё сообщение именно как текст правки, а не как новый форвард.
- **`control/handlers.py`** — сама логика:
  - `/start` — приветствие;
  - обработчик пересланных сообщений — берёт текст форварда, прогоняет через `run_pipeline`, показывает карточку с пометкой вердикта (✅/⚠️/🔴) и списком нарушений, если они есть;
  - `send:` — помечает черновик отправленным, дописывает его в историю как исходящее сообщение (сам текст в Telegram-чат с заказчиком в стадии 1 не улетает — это делаешь ты, копируя текст; бот только ведёт учёт);
  - `skip:` — помечает черновик пропущенным;
  - `edit:` → `EditDraft.waiting_for_text` — просит новый текст, **и вот здесь снова вызывается guard** (`recheck_edited_text`), на этот раз на твоей правке. Это тот самый механизм из архитектуры: кнопка "Изменить" не становится обходом проверки.
- **`app.py`** — точка входа: создаёт бота, диспетчер с `MemoryStorage` для FSM, подключает роутер, запускает polling (бот сам опрашивает Telegram на новые сообщения — простой способ для разработки, не требует своего сервера с открытым портом).

**Почему MemoryStorage, а не Redis.** Для стадии 1 количество одновременных правок небольшое, а если бот перезапустится посреди правки — не страшно потерять состояние "жду текст", черновик всё равно останется в базе. Если это станет проблемой при росте нагрузки, меняется на `RedisStorage` без переделки `handlers.py` — aiogram сам абстрагирует хранилище FSM.

**Как проверил.** Импортировал `app.py` целиком — все модули подключились без ошибок, 6 обработчиков зарегистрировались в роутере. Запустил бота по-настоящему (`python -m talking_bot.app`) — в логе `Start polling` без ошибок, значит токен верный и Telegram принял соединение.

## Шаг 13 — импорт готовой истории переписки

**Задача.** Ты уже месяц ведёшь переписку с заказчицей напрямую в Telegram — весь этот контекст должен попасть в бота одним разом, а не собираться заново форвардами. Плюс нужен способ находить конкретный фрагмент старого разговора по ключевым словам.

**Как загружаем.** Telegram Desktop умеет экспортировать всю историю чата в JSON-файл (⋮ → Экспорт истории чата). Бот принимает этот файл командой `/import_file`.

### `ingest/telegram_export.py` — разбор файла экспорта

**Что сделали.** Функция `parse_export`, которая читает файл экспорта и превращает его в список сообщений с текстом, направлением (входящее/исходящее) и реальным временем отправки.

**Самое нетривиальное место — определение направления.** В экспорте личного чата оба участника выглядят в JSON одинаково по структуре — единственное, что их отличает, это `from_id`. Поэтому при импорте нужно явно сказать боту, какой `from_id` — твой (например `user361963836`), иначе все 545 сообщений определятся как одно направление, и черновики будут писаться так, будто заказчик говорит твоим голосом.

**Второе нетривиальное место — текст с форматированием.** В экспорте поле `text` не всегда простая строка — Telegram кодирует жирный текст, ссылки и упоминания как список кусков вида `{"type": "bold", "text": "..."}`. Парсер достаёт из этого только читаемый текст — guard и compose работают со смыслом, а не с разметкой.

**Что осознанно пропускается.** Сообщения без текста (только фото, видео, файл) и служебные записи (изменение названия чата и т.п.) в базу не попадают — в переписке с заказчицей таких оказалось 59 из 604. Вложения — отдельная задача, не тянем её сюда неявно.

**Как проверил — не на выдуманных данных, а на реальном экспорте.** Прогнал парсер на твоём настоящем `result.json` с перепиской (604 сообщения, 545 с текстом). Первое распознанное сообщение — «добрый день Владимир», это действительно первая фраза диалога. Направления (211 исходящих, 334 входящих) совпали с ожиданием.

## Баг №2 — импорт молча портил время сообщений

**Что случилось.** После первого прогона импорта на реальных данных все 545 сообщений в базе получили **одну и ту же метку времени** — момент запуска скрипта, а не настоящее время из переписки (25 июля – 26 августа). Тест на количество сообщений прошёл бы зелёным — баг нашёлся только потому, что отдельно проверил сами даты в базе, а не только факт наличия строк.

**В чём была причина.** `add_message` в `domain/dialog.py` изначально всегда писал `datetime.now(timezone.utc)` — это было правильным для живого бота (сообщение только что пришло), но не подходило для импорта, где у каждого сообщения уже есть своя настоящая дата. Функция просто не умела принять время снаружи.

**Как исправили.** Добавил `add_message` необязательный параметр `sent_at`: если не передан — берётся текущее время (обычный случай), если передан — используется он (случай импорта). Заодно поправил `get_recent_messages`: раньше сортировка шла по `id` (порядок вставки в базу), теперь — по `sent_at` (реальное время сообщения). Для живого бота разницы нет, но после импорта это разные вещи, и `compose` должен видеть историю в правильном хронологическом порядке, а не в порядке, в котором сообщения оказались в файле экспорта.

**Как проверил, что починилось.** Повторный импорт → в базе первое сообщение действительно от 25.07, последнее — от 26.08, разброс дат совпадает с реальной перепиской, а не сжат в одну секунду.

## Шаг 14 — поиск по истории (`/find`)

**Что сделали.** Команда `/find <фраза>` — ищет фразу по всем сообщениям диалога (`ILIKE '%фраза%'`, регистронезависимо), возвращает до 10 совпадений с датой, стрелкой направления (`→` — твоё сообщение, `←` — заказчика) и фрагментом текста вокруг найденного слова.

**Почему обычный поиск по подстроке, а не "умный" семантический.** Для объёма в несколько сотен сообщений в одном диалоге простой и предсказуемый поиск лучше: ты точно знаешь, что получишь — все места, где встречается именно эта фраза, без риска, что "умный" поиск решит, будто что-то не подходит по смыслу, и пропустит нужную цитату. Семантический поиск (эмбеддинги, векторная база) — это то, что ты обсуждал с заказчицей для её собственного RAG-проекта, тот подход overkill для личного инструмента на один диалог.

**Как проверил.** На реальных импортированных данных — три запроса: `видео` (10 совпадений, все по делу), `пиджак` (6 совпадений, все реальные упоминания в разных контекстах переписки), и заведомо ошибочный `graдация` (0 совпадений, без мусора). Даты и направления в выдаче совпадают с реальной перепиской.

## Как загрузить свою переписку прямо сейчас

1. В Telegram Desktop открой чат с заказчиком → ⋮ → Экспорт истории чата → формат **JSON**, без медиафайлов.
2. Пришли получившийся `result.json` боту как файл, с подписью `/import_file <твой_from_id>` (свой `from_id` можно узнать, открыв файл текстом — он в поле `"from_id"` у твоих собственных сообщений).
3. Бот загрузит историю и напомнит: плана переговоров для диалога ещё нет, `guard` пока будет отвечать "план пуст".
4. Дальше — `/find <слово>`, чтобы находить нужные места в истории.

## Баг №3 — бот не отвечал на сообщения вообще

**Что случилось.** Спросил "почему бот не реагирует" — оказалось, процесс бота был не запущен: он умер сразу после старта, гораздо раньше, ещё в момент первого запуска в шаге 12, и с тех пор просто не работал. В логе было `Start polling`, что выглядело как успех, но сразу под этим — `TelegramNetworkError: Request timeout error`.

**В чём была причина — не в коде, а в сети.** Проверил напрямую: `curl https://google.com` отвечает быстро, `curl https://api.telegram.org` — не отвечает совсем, таймаут. Значит дело не в коде бота и не в токене, а в том, что сам сервер, на котором всё это крутится, не может достучаться до Telegram API — типичная ситуация для машины в стране/у провайдера, где Telegram заблокирован на сетевом уровне.

**Почему это не было заметно раньше.** `dispatcher.start_polling()` печатает `Start polling` до того, как реально успешно подключится — сам первый запрос (`bot.me()`, "кто я") уже происходит внутри и там же падает с таймаутом. Строка в логе создавала ложное впечатление, что всё запустилось.

**Как исправили.** Код сам сеть не чинит — почитать блокировку код не может. Добавил в бота **поддержку прокси**: настройка `PROXY_URL` в `.env` (пусто по умолчанию — работает как раньше). Если она задана, весь трафик к Telegram идёт через указанный HTTP- или SOCKS5-прокси вместо прямого соединения. Заодно поставил `aiohttp-socks` — без него aiogram не умеет ходить через `socks5://` адреса.

**Что нужно от тебя, чтобы бот заработал.** Поднять VPN или прокси на сервере (или воспользоваться уже готовым — ты упоминал, что для боевого проекта заказчицы такой сервер уже есть), вписать его адрес в `.env` в строку `PROXY_URL=socks5://...` (сейчас закомментирована — раскомментировать и подставить реальный адрес). После этого бот нужно перезапустить.

**Уточнение после повторной проверки: сеть не заблокирована наглухо, а нестабильна.** При прямой проверке (`curl api.telegram.org` несколько раз подряд) три попытки из четырёх дали таймаут, одна прошла успешно. Один прямой запуск бота (`timeout 20`) действительно подключился с первой попытки — но это оказалось везением: следующий запуск в фоне ждал дольше минуты и всё равно упал с той же `TelegramNetworkError: Request timeout error`.

**Настоящая причина — не блокировка Telegram, а среда разработки.** Выяснилось, что вся работа с самого начала шла не на выделенном сервере, а на **домашнем компьютере под Windows через WSL2** (Linux-подсистема Windows) — это стало понятно, когда в `docker ps` обнаружились чужие контейнеры (`clothing-ai-*`, отдельный проект). У WSL2 есть известная особенность: сетевой мост между Windows и Linux иногда рвётся сам по себе — при смене Wi-Fi/VPN, засыпании ноутбука, автообновлении сетевых драйверов. Именно поэтому `curl` то отвечал мгновенно, то падал с `Network is unreachable` — не Telegram решал пускать или нет, а сам мост то был, то пропадал, причём это било и по Google точно так же.

**Почему у `@LekalaEtalonAIBot` (боевой бот заказчицы) такой проблемы нет.** Он работает на отдельном VPS в Нидерландах (`hostkey.ru`) — это дата-центр с постоянным подключением, без домашней сети и без WSL2 между ботом и интернетом.

**Что это значит для дальнейшей работы.** `PROXY_URL` в коде остаётся — это универсальный механизм, полезный, если бот когда-нибудь окажется за настоящей блокировкой. Но проблема с обрывами сейчас — это не про Telegram и не про код, а про то, что **бот для разработки временно живёт на нестабильной домашней сети**. Решили: пока это нормально, продолжаем разработку здесь, бот не обязан быть онлайн 24/7 во время написания кода. Когда дойдёт до реальной работы с заказчиками — переносить на сервер (например, тот же VPS в Нидерландах, где уже крутится боевой бот).
